## Резюме

1. **Алгоритм цепной реакции корректен.** Он детерминирован, математически завершим (доказано, см. §2.4), фактически локален (0–2 % «посторонних» переносов) и не содержит дефектов, порождающих некорректные каскады. Предположение «алгоритм работает неправильно» не подтвердилось.

2. **Проблема «торты собираются слишком часто» подтверждена и измерена**, но её характер иной, чем кажется: не «чудовищные каскады за один ход» (максимум 4 торта за ход, ≥2 тортов лишь в 5 % ходов), а **слишком высокая средняя частота** — торт собирается примерно **в каждом втором ходу** (49 % ходов у жадного игрока), и за ход **автоматически** поле покидают в среднем 1.08 тарелки. Из-за этого стол никогда не оказывается под давлением (в среднем 5.4 свободных ячейки из 9), выбор места размещения почти не влияет на результат (в 59 % состояний все допустимые ходы дают одно и то же число тортов), и партия проходит почти «на автопилоте» за 5–24 хода.

3. **Причина — не в цикле разрешения, а в трёх системных факторах:** «аккумуляторный эффект» правила получателя + неограниченная дальность цепочек на 3×3 + мелкий состав тарелок выдачи (§4).

4. **Проверены все типы ограничений из ТЗ 3.4 на одинаковых сидах** (§5). Результат: лимит тортов за ход и лимит переносов **не меняют частоту** (лишь откладывают сборки и порождают патологию «6 одинаковых кусочков, но торт не собирается» — ровно ту, о которой предупреждало ТЗ); полный запрет цепочек ломает проходимость на текущих целях (2/30 побед у жадного); ограничение локальности ничего не меняет (каскад и так локален). **Единственный рычаг, реально меняющий баланс, — максимальная дальность цепочки**, и он предлагается не как «тормоз каскада», а как параметр сложности уровня (§6.3).

5. **Предложение по Этапу B** (§6): фазовая переработка разрешения с журналом событий (поведение идентично текущему, проверяется тестом эквивалентности), `CascadeConfig` с защитным лимитом шагов, параметр `maxChainHops` в конфигурации уровня с перенастройкой кривой целей, волновой визуальный темп. Тестовые сценарии — в §6.5.

## 2. Фактическая схема текущего алгоритма

### 2.1 Какие события запускают проверку поля

**Единственное** событие — размещение тарелки игроком: `placePlate()` → `runResolution(cells)`. Проверка поля после этого выполняется до полной стабилизации в пределах одного вызова.

Не запускают проверку (и не могут создать перенос): пополнение очереди (`topUpTray`), поворот двойной тарелки, проигрывание анимаций. В конце каждого хода поле всегда полностью «расслаблено» — допустимых переносов не остаётся, поэтому все переносы следующего хода причинно связаны с новым размещением (это подтверждает и 0–2 % «посторонних» переносов, §3.1).

### 2.2 Цикл разрешения (`rules.ts → resolveTurn`; `engine.ts → runResolution` повторяет его пошагово для анимации)

```
Размещение тарелки (placeSingle / placeDouble; lastPlaced = ячейки размещения)
   │
   ├─ findCompletion?  ── да → applyCompletion (торт, очки, ячейка свободна)
   │
   └─ цикл ─────────────────────────────────────────────────────┐
        │  planNextTransfer(state, lastPlaced)                  │
        │    1) ПРЯМЫЕ ПЕРЕНОСЫ: обход ячеек по строкам,        │
        │       соседи только «вправо» и «вниз», вкусы          │
        │       по возрастанию → первая подходящая пара          │
        │    2) если прямых нет — ЦЕПОЧКИ: от каждой ячейки      │
        │       по каждому вкусу, BFS по соседним тарелкам       │
        │       со свободным местом (транзит), кратчайший        │
        │       детерминированный маршрут                        │
        │  нет переносов → выход из цикла                        │
        │  да → applyTransfer (кусочки вкуса перелетают,         │
        │       пустой донор удаляется, +2 очка/кусочек)         │
        │       └─ findCompletion? ── да → applyCompletion ──────┘
   │
   └─ evalEnd: победа по очкам / поражение (full/leftover) / играем дальше
```

Направление переноса определяет `chooseRecipient`: побеждает тарелка, где этого вкуса **больше**; при равенстве — размещённая в текущем ходе; при равенстве — меньший индекс ячейки. Целый торт — 6 одинаковых кусочков на тарелке.

### 2.3 Порядок обработки совпадений

Прямые переносы имеют **абсолютный приоритет** над цепочками (сначала весь обход прямых пар, только затем цепочки). Внутри — порядок обхода ячеек (по строкам, «вправо/вниз») и вкусы по возрастанию. Это уже даёт «приоритет прямых совпадений перед длинными цепочками» из ТЗ 3.4 — он в игре есть.

### 2.4 Завершимость (защита от бесконечных циклов)

Каждый перенос перемещает **все** кусочки одного вкуса с донора (донор теряет вкус полностью; получатель этот вкус уже имел — как в прямом переносе, так и в цепочке). Следовательно, каждый перенос уменьшает на 1 величину `Σ_вкусов (число тарелок, содержащих вкус)` — внутри разрешения она не может расти. Верхняя оценка числа переносов за ход: 9 тарелок × 6 вкусов = 54. Фактический максимум за 1000+ ходов — **6 переносов**. Бесконечный цикл в текущих правилах невозможен математически; `CascadeConfig.maxResolutionSteps` нужен только как страховка на случай будущих изменений правил (и для диагностики), а не как рабочий ограничитель.

### 2.5 Повторное участие тарелок

Максимум участий одной тарелки в переносах за ход — 6 (в среднем 1.93); максимум повторов одной пары тарелок — 4 (в среднем 1.17). Повторы законны: тарелка может отдать вкус A, затем принять вкус B, затем уйти с поля. Патологий (осцилляций) не выявлено.

### 3.4 Анатомия самого бурного хода

Максимум за все партии: **6 переносов за ход**; худший по тортам ход — 4 торта за 4 переноса (уровень 13, ход 14, 1 случай на 486 ходов жадного):

```
1. вкус 13 ×2: 8→5→2→1 (цепочка) → ТОРТ
2. вкус 5  ×1: 7→8→5→2 (цепочка) → ТОРТ
3. вкус 7  ×2: 7→4→3   (цепочка) → ТОРТ
4. вкус 10 ×1: 8→5→4   (цепочка) → ТОРТ
```

Одно размещение — четыре цепочки через пол-стола, каждая собрала торт. Заметно: ячейки 5 и 8 работают транзитом по два раза. По текущим таймингам анимации такой ход занимает ~10 секунд чистого просмотра.

### 3.5 Значимость выбора игрока (агентность)

Для 179 состояний (первые ходы каждого уровня) перебраны **все** допустимые ходы (в среднем 29 на состояние), каждому — полное разрешение:

- в **59 %** состояний все ходы дают **одинаковое число тортов**;
- разброс очков между лучшим и худшим ходом: в среднем 48 (половина стоимости торта), максимум 237;
- жадный игрок обгоняет случайного лишь на 12 % по длине партии (16.2 против 18.1 хода) и на 10 п.п. по победам.

**Вывод: выбор игрока в текущем балансе слабо влияет на исход хода** — поле почти всегда «расслабляется» до одного и того же состояния почти независимо от места размещения.

## 4. Диагноз: почему торты собираются слишком часто

**П1. Аккумуляторный эффект правила получателя (главная причина).**
`chooseRecipient` всегда отдаёт кусочки тарелке, где этого вкуса больше. Вместе с цепочками (любая тарелка со свободным местом — транзит) это означает: каждый вкус на столе стекается в одну «тарелку-аккумулятор». При пуле ≤6 вкусов и столе 3×3 практически всегда есть 2–4 аккумулятора с 3–5 кусочками одного вкуса — и **любая** размещённая тарелка с этим вкусом достраивает торт, откуда бы её ни поставили. Частота тортов задаётся скоростью поступления кусочков, а не решениями игрока.

**П2. Стол не находится под давлением.**
Авто-очистка (1.08 тарелки/ход) компенсирует размещения: в среднем 5.4 свободных ячейки, у жадного минимум 3. Поражение практически недостижимо (30/30 и 27/30 побед). Пространственная головоломка «куда ставить» не включается: размещение возможно почти в любую ячейку, и результат от этого почти не зависит (§3.5).

**П3. Неограниченная дальность цепочек на 3×3.**
На поле 3×3 BFS через тарелки со свободным местом почти всегда соединяет любые две тарелки (макс. маршрут — 7 тарелок). Размещение тарелки — часто просто «открытие нового транзита», после которого сходятся далёкие вкусы (см. трассировку §3.4). Именно поэтому ходы ощущаются «домино»: одна причина тянет цепь следствий через весь стол.

**П4. Ощущение автоматичности усиливается подачей.**
Комбо-бонус (+25 за каждый следующий торт хода) поощряет мульти-сборки, а анимация строго последовательна (~2.4 с на торт) — бурный ход превращается в длинный «киносеанс» без участия игрока.

**Что НЕ является причиной:** дефекты цикла разрешения (их нет — §2), «посторонние» переносы (0–2 %), генератор «почти тортов» (2.5 % — незначимо, вариант G4 это подтвердил).

## 5. Проверка ограничений каскада (ТЗ 3.4–3.5) на одинаковых сидах

Все варианты играются жадным игроком на тех же 30 уровнях. «Оборвано» — ходов, где лимит остановил разрешение до стабилизации поля.

| Вариант | Побед | Ходов | Торт/ход | Макс т. | ≥2 т. | Перен./ход | Своб. яч. | Оборвано |
|---|---|---|---|---|---|---|---|---|
| **V0 текущая** (без лимитов) | 30/30 | 16.2 | 0.54 | 4 | 5 % | 2.12 | 5.42 | 0 |
| V1 максимум 1 торт/ход | 30/30 | 16.6 | **0.54** | 1 | 0 % | 2.10 | 5.10 | **267** |
| V2 максимум 4 переноса/ход | 30/30 | 16.1 | 0.55 | 4 | 7 % | 2.13 | 5.35 | 49 |
| V3 цепочки выключены | **2/30** | 7.5 | 0.10 | 2 | 0 % | 1.20 | 2.76 | 0 |
| V4 только «вовлечённые» тарелки | 30/30 | 16.2 | 0.55 | 4 | 6 % | 2.14 | 5.40 | 0 |
| H2 цепочка ≤2 прыжков (1 транзит) | **21/30** | 16.8 | **0.44** | **2** | 6 % | 2.02 | **3.97** | 0 |
| H3 цепочка ≤3 прыжков | 30/30 | 16.1 | 0.54 | 4 | 6 % | 2.14 | 5.27 | 0 |
| H4 цепочка ≤4 прыжков | 30/30 | 16.2 | 0.54 | 4 | 5 % | 2.12 | 5.42 | 0 |

Контроль на случайном игроке: V0 — 28/30 побед, H2 — 15/30, H3 — 24/30.

Выводы по вариантам:

- **V1 (лимит тортов) отклонён.** Частота не изменилась (0.54) — торт, «отложенный» лимитом, собирается в начале следующего хода (собранные 6 кусочков проверяются до переносов). При этом 267 ходов из ~500 оборваны до стабилизации, то есть в половине ходов поле остаётся в «недособранном» состоянии — ровно та патология «6 одинаковых кусочков, но торт не собирается», о которой предупреждало ТЗ 3.4. Ограничение не решает проблему и разрушает целостность правил.
- **V2 (лимит переносов) отклонён** как самостоятельный инструмент: эффект статистически неотличим (49 оборванных ходов из ~500), причину не устраняет.
- **V3 (без цепочек) ломает игру**: 2/30 побед. Цепочки — несущая механика на 3×3; данные подтверждают необходимость их сохранить.
- **V4 (локальность) отклонён**: каскад и так локален (0 % посторонних переносов), ограничение не меняет ни одной метрики.
- **H2/H3/H4 (дальность цепочки) — единственный параметр с доказанным эффектом.** Ограничение «2 прыжка» (одна транзитная тарелка): торт/ход −19 % (0.54→0.44), максимум тортов за ход 4→2, давление на стол +37 % (5.42→3.97 свободных ячеек), доля цепочек сохраняется (43 %) — головоломка «прокладывания маршрута» остаётся. Цена: на текущих целях жадный выигрывает лишь 21/30 — **цели нужно перенастраивать одновременно**. H3/H4 на 3×3 практически равны текущему поведению (цепочки длиннее 3 прыжков редки).

Дополнительно проверены конфигурации генератора (те же правила, другой состав выдачи): «всегда 3 вкуса на тарелке» — 0.68 торт/ход (больше), «пул 5/7 вкусов» — 0.61/0.56, «без чистых и тяжёлых тарелок» — 0.60. Состав выдачи в разумных пределах двигает частоту в диапазоне 0.42–0.77, но качественно картину не меняет: частота тортов ≈ (кусочков за ход) / 6 — определяется потоком материала.

## 6. Предложение по изменению алгоритма (на Этап B)

### 6.1 Фазовое разрешение с журналом событий (поведение без изменений)

Разделить `resolveTurn` на явные фазы ТЗ 3.3 и вернуть из него **журнал событий** вместо «тихого» изменения состояния:

```ts
type TurnEvent =
  | { kind: 'place'; cells: CellIndex[] }
  | { kind: 'transfer'; transfer: Transfer }          // перенос с маршрутом
  | { kind: 'cake'; cell: CellIndex; flavor: Flavor; combo: number; points: number }
  | { kind: 'plateGone'; cell: CellIndex }
  | { kind: 'phase'; phase: 'detect' | 'move' | 'bake' | 'cleanup' | 'recheck' | 'done' };

resolveTurnLogged(state, lastPlaced, cfg): TurnEvent[]
```

Требование эквивалентности: на всех 30 уровнях и на сценарных тестах итоговое состояние и очки после `resolveTurnLogged` совпадают с текущим `resolveTurn` (тест-двойник уже есть в `audit-cascade.ts` — кросс-проверка §1). Журнал — это контракт для визуального слоя (ТЗ 3.7: «анимация не определяет игровую логику»), для подсказки и для симулятора Этапа C.

### 6.2 CascadeConfig (ТЗ 3.5) — защита, а не балансировка

```ts
interface CascadeConfig {
  maxResolutionSteps: number;      // ЗАЩИТНЫЙ лимит (по умолчанию 64; доказанный максимум — 54)
  maxTransfersPerTurn: number;     // по умолчанию Infinity — отключено
  maxCakesPerTurn: number;         // по умолчанию Infinity — отключено
  allowChainTransfers: boolean;    // true — выключение ломает игру (данные §5)
  maxChainHops: number;            // дальность цепочки; Infinity = как сейчас (см. 6.3)
  directTransferPriority: boolean; // true — уже реализовано, фиксируется явно
}
```

Лимиты переносов и тортов остаются в конфиге (отключёнными): данные §5 показывают их бесполезность как балансировщика, но структура из ТЗ сохраняется для будущих режимов. Срабатывание `maxResolutionSteps` — не «обрубание», а безопасное завершение с диагностикой (сид, номер хода, снимок поля), состояние остаётся консистентным (ТЗ 3.6). Удалять тарелки и кусочки для завершения обработки запрещено.

### 6.3 Дальность цепочки — параметр сложности (главное предложение)

Внести `maxChainHops` в конфигурацию уровня и использовать в прогрессии (совместно с перенастройкой кривой целей `targetFor`):

- **Ранние уровни (обучение):** без ограничения — длинные эффектные цепочки знакомят с правилом соседних тарелок.
- **Средние/поздние уровни:** 2 прыжка (один транзит) — по данным H2: торт/ход −19 %, «бурные» ходы максимум 2 торта, стол реально заполняется (3.97 своб. ячеек), выбор места и маршрута становится значимым.
- **Крупные поля (3×4, 4×4 — Этап E):** дальность — готовый регулятор сложности без изменения правил; на больших полях 2 прыжка оставят больше локальных решений, чем на 3×3 (проверить симулятором Этапа C).

**Обязательное условие:** одновременная перенастройка целей — при H2 и текущих целях жадный игрок выигрывает 21/30, то есть часть уровней становится труднопроходимой. Подбор новой кривой — работа Этапа B/C на симуляторе (инструмент готов).

Терминология: «2 прыжка» = маршрут «донор → 1 транзитная тарелка → получатель»; прямой перенос — «1 прыжок». Ограничение не запрещает длинные перемещения как класс: игрок планирует многоходовые маршруты из коротких сегментов — и именно это становится головоломкой.

### 6.4 Визуальный темп (ТЗ 3.7)

Журнал событий (6.1) даёт естественную основу:

- **Волны:** события, не связанные общими тарелками, анимируются одновременно (сейчас — строго по одному). Серийность: «торт за тортом» в комбо — ускорять каждую следующую сборку (2.4 → 1.6 → 1.1 с) с общим счётчиком серии на экране.
- **Подсветка маршрута** цепочки перед полётом (транзитные тарелки подсвечиваются по мере пролёта — сейчас есть искры, усилить контуром получателя).
- **Индикация завершения хода**: короткий сигнал «стол успокоился» перед возвратом управления игроку.

### 6.5 Тестовые сценарии для Этапа B

1. Эквивалентность `resolveTurnLogged` ↔ `resolveTurn` на уровнях 1–30 (состояние + очки, оба игрока).
2. Журнал событий воспроизводим на одинаковых входах (детерминизм).
3. `maxChainHops = 1/2/3/∞`: перенос запрещён/разрешён через N транзитов; границы поля, углы, диагонали.
4. Транзит только через тарелку со свободным местом (полная блокирует) — при всех значениях hops.
5. `maxResolutionSteps`: при искусственно заниженном лимите поле остаётся консистентным, игра не блокируется, пишется диагностика.
6. После переноса с освобождением донора ячейка доступна и учитывается в следующих фазах того же хода.
7. Комбо: сбрасывается новым ходом, растёт внутри хода, очки по формуле.
8. Победа по очкам: торт, собранный последним событием хода, засчитывается до `evalEnd`.
9. Двойная тарелка: обе ячейки в `lastPlaced`, приоритет получателя при равенстве.
10. Прогрессия `maxChainHops` из конфига уровня читается и применяется; при `∞` поведение идентично текущему.

## 8. Нерешённые вопросы (нужны решения до/в Этапе B)

1. **Целевая частота тортов.** Сейчас торт в 49 % ходов. Рабочая гипотеза для проверки: 25–35 % ходов — «праздник остаётся праздником». Какая цифра целевая?
2. **Допустимая доля поражений.** Сейчас жадный выигрывает 100 %, случайный ~90 %. Проигрывать должно быть возможно, но редко. При H2 жадный — 70 %. Совместно с перенастройкой целей нужно согласовать коридор (например, жадный 95–100 %, случайный 40–70 %).
3. **Комбо-бонус** поощряет мульти-сборки (П4). Оставить как есть (правила очков не меняем без отдельного решения, ТЗ 14.7) или учитывать при перенастройке?
4. **Применять ли H2 ко всем уровням или в прогрессии** (обучение на длинных цепочках, затем ограничение)? Моя рекомендация — в прогрессии.

## Приложение. Как воспроизвести аудит

```bash
npx tsx scripts/audit-cascade.ts
```

Скрипт не требует браузера и не изменяет игровые правила; все экспериментальные варианты каскада живут внутри скрипта. Секции вывода: кросс-проверка → текущие правила (2 игрока) → сравнение вариантов каскада → контроль на случайном игроке → срез по уровням → агентность → заполненность → анатомия бурных ходов → эксперименты с составом выдачи.
